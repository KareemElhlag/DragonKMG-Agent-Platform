# خطة سبرنت الإضافات والربط

التحديث2026-10-15: تم تجهيز تجربة GitHub للقراءة وربط الحساب عبرPAT؛ اختبار الحساب الخاص الحي ينتظر إدخال المستخدم رمزه. LinkedIn وGmail مخططان فقط. لا تمنح واجهة الشات صلاحيات أدوات تلقائيًا. راجع `GITHUB_INTEGRATION.ar.md` و`CHAT_GITHUB_VERIFICATION.ar.md`.

## واجهة الشات الحالية

اختيار مجلد المشروع وإضافته فوق مربع الإرسال، وبجانبه مدخل الإضافات والربط.
المشروع مجلد وليس ملفًا؛ اختيار الملفات للسياق منفصل ولا تعني إضافة المشروع قراءة محتوياته تلقائيًا.

## ترتيب التنفيذ المقترح

1. GitHub: ربط الحساب واختيار المستودعات صراحةً؛ القراءة أولًا، ثم كتابة التغييرات بموافقات مستقلة.
2. LinkedIn: التحقق من إمكانات الواجهة الرسمية والصلاحيات المتاحة للحساب قبل الالتزام بوظائف؛ إعداد مسودات أولًا، ولا نشر تلقائيًا.
3. Gmail: قراءة محددة النطاق، ثم المسودات؛ الإرسال يحتاج موافقة واضحة على المستلمين والمحتوى.
4. إضافات أخرى من كتالوج موحد بعد نجاح دورة الربط والقطع والتدقيق.

## بنود السبرنت ومعايير القبول

- [ ] سجل موحد للإضافات وإمكاناتها وحالة الاتصال، دون أزرار وهمية.
- [ ] تصميم OAuth حسب متطلبات كل مزود، والتحقق من state/PKCE حيث ينطبق، وتخزين الأسرار في الخزنة لا المتصفح أو السجلات.
- [ ] ربط الصلاحيات بالمستخدم والمشروع والفريق؛ مهارات التعليمات لا تمنح أدوات.
- [ ] قائمة أدوات مسجلة، أقل صلاحيات، وموافقة بشرية قبل الأعمال الخارجية الحساسة.
- [ ] سجل تدقيق دائم منقح من الأسرار، مع فصل القراءة عن النشر والإرسال.
- [ ] حدود الطلبات والمهل وإلغاء التنفيذ، ومنع تكرار عمليات الكتابة عند إعادة المحاولة.
- [ ] قطع الاتصال وإبطال الرموز ومعالجة انتهاء التفويض.
- [ ] اختبارات رفض الوصول والتفويض المنتهي وتكرار الطلبات وعزل الحسابات، ثم تجربة حية بحساب اختبار مصرح به.

لا يتضمن هذا السبرنت المخطط وعدًا بتوفير كل إمكانات المزود؛ تبدأ كل إضافة بمراجعة الواجهة الرسمية وشروط الإتاحة وقت التنفيذ.
