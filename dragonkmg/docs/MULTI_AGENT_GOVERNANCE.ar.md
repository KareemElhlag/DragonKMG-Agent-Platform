# التوثيق الهندسي: تشغيل وحوكمة الفرق متعددة الوكلاء

تاريخ المراجعة: 2026-10-15. المرجع هو التنفيذ الحالي، وليس وصف النموذج لنفسه. نميز هنا بين قدرات المنتج، وسياسة فريق التطوير، والقدرات المستهدفة.

## 1. الوكلاء قابلون للتخصيص

الثلاثة في المجلس الافتراضي **قالب بداية، وليسوا حدًا أقصى لإنشاء الوكلاء**. يمكن إنشاء فريق مخصص من خمسة أو أكثر؛ هذا لا يعني سعة تشغيل غير محدودة أو ضمان أداء لأي عدد.

| الإعداد | المتاح حاليًا |
| --- | --- |
| الدور والتعليمات | ربط الوكيل بدور وإضافة تعليماته الخاصة. |
| النمط | تنفيذ، تخطيط فقط، سؤال فقط، أو مراجعة. القيود تعليمات للنموذج، وليست sandbox. |
| الاتصال والموديل | ربط مستقل لكل وكيل؛ الاتصال الافتراضي لا يمنع اختيار اتصال آخر. |
| المهارات | تعليمات مكتوبة أو من ملف مشروع، وتعيينات مستقلة قابلة للتفعيل والتعطيل والترتيب. |
| الأدوات | منح منفصل عن المهارات؛ إضافة مهارة تعليمية لا تمنح صلاحيات أداة. |
| ترتيب التنفيذ | مراحل Workflow مرتبطة بالوكلاء، واعتماديات وقوائم تحقق وأدلة متوقعة. |

إنشاء القالب ينشئ الأعضاء الناقصين ويربط المهارات الافتراضية بالأعضاء الجدد، ولا يعيد كتابة إعدادات الموجودين. يمكن إزالة تعيينات المهارات واستبدالها بمهارات مخصصة. المهارات المنسوخة للمشروع تحت `skills/`؛ راجع [واجهة الإدارة](UI_CONTROL_CENTER.md).

## 2. متى يعمل المجلس؟

محادثة الجلسة تتطلب فريقًا محددًا للطلب أو فريقًا افتراضيًا محفوظًا للجلسة؛ غياب الاثنين يطلب الاختيار دون استدعاء موديل. الفريق قد يحتوي وكيلًا واحدًا أو عدة أعضاء مرتبين. راجع [إعداد الفرق وتوجيه البرومبت](TEAMS.ar.md). قالب المجلس الثلاثي يعمل باستدعاء مساره الصريح؛ والـWorkflow المخصص يعمل باستدعاء مسار تشغيله. **لا يوجد مصنّف تلقائي يفعّل المجلس بناءً على حجم المهمة.**

السياسة الهندسية الموصى بها للاختيار:

1. استخدم فريقًا عندما تحتاج مراجعة مستقلة أو تخصصات متعددة، أو عندما تكون المخاطر مرتفعة حتى لمهمة صغيرة.
2. حدد المسؤوليات والأدلة ومعايير القبول قبل التشغيل.
3. عند تنفيذ متوازٍ مستقبلًا، حدد مجموعات كتابة غير متداخلة أو آلية قفل/تسلسل مناسبة.
4. المهام البسيطة قد تناسب مرور وكيل واحد لتقليل الوقت والتكلفة عندما لا تحتاج مراجعة مستقلة.

هذه سياسة تنظيمية، لا شروط يكتشفها المحرك حاليًا. لا توجد آلية عامة لقفل الملفات أو إعادة التحكم تلقائيًا إلى المنظم عند تعارض الكتابة. سياسة التعارض المطلوبة هي إيقاف الإجراء المتأثر وإعادته للمنظم؛ لا ينبغي وصفها كميزة منفذة.

## 3. المجلس الافتراضي المنفّذ

القالب يعرّف ثلاثة وكلاء وأربع خطوات تعليمية عبر ثلاثة استدعاءات متتابعة:

1. **Execution Agent:** التوضيح والتخطيط ثم التنفيذ والتحقق في الاستدعاء نفسه.
2. **Quality Review Agent:** مراجعة الجودة والهيكل وتجربة الاستخدام والأدلة.
3. **Security Test Agent:** مراجعة دفاعية للأمان والاختبارات والأدلة.

كل مرحلة تتلقى الطلب الأصلي وأدلة محدودة الحجم من المراحل السابقة. فشل الاستدعاء يوقف بقية السلسلة. اكتمال الاستجابة ليس إثبات تنفيذ تغييرات أو نجاح اختبارات فعلية. قوائم التحقق تعليمات للنموذج؛ لا يوجد تحقق آلي من صحة كل بند أو تفسير إلزامي لحكم المراجع.

## 4. فريق مخصص من خمسة أدوار

يمكن تكوين هذا الفريق يدويًا؛ ليس هو المجلس الافتراضي المشغل تلقائيًا:

| الدور | المسؤولية المقترحة | نطاق العمل المتفق عليه |
| --- | --- | --- |
| Implementer | تطبيق التغيير وإنتاج الأدلة. | مجموعة ملفات محددة. |
| Reviewer / Fixer | مراجعة الصحة والهيكل والاختبارات. | قراءة، وأي كتابة تحتاج نطاقًا صريحًا. |
| Security Agent | مراجعة التفويض والأسرار والحدود. | فحوصات دفاعية مصرح بها. |
| UX Agent | مراجعة التدفقات والتفاعل والإتاحة وRTL والاستجابة. | فحص مرئي وتفاعلي؛ ليس مجرد فحص سطحي. |
| Senior Monitor | الاعتماد النهائي بناءً على الأدلة. | مستقل؛ لا يصادق على عمله الخاص. |

المنظم مسؤولية تنسيق، وليس بالضرورة وكيلًا سادسًا أو استدعاء موديل إضافيًا. يمكن تمثيله كوكيل مخصص إذا احتاج التصميم لذلك. حالات `CERTIFIED` و`CERTIFIED_WITH_RESIDUE` و`REWORK_REQUIRED` و`BLOCKED` اتفاق تقرير في مهارات التطوير؛ ليست آلة حالات اعتماد ينفذها محرك المجلس حاليًا.

## 5. إعداد وتشغيل Workflow مخصص

1. أنشئ الاتصالات والموديلات ثم الأدوار والوكلاء.
2. عيّن المهارات المناسبة لكل وكيل وراجع إعداداته الفعلية ومنحه.
3. عرّف مراحل بأسماء ومعرفات وترتيب فريد، وحدد الوكيل وقائمة التحقق والأدلة المتوقعة.
4. اربط المراحل باعتماديات صريحة بلا دورات أو ارتباط المرحلة بنفسها.
5. احفظ التعريف ثم شغّله. المحرك ينفذ المراحل الجاهزة **بالتتابع** وفق `Position`؛ وجود فروع مستقلة لا يعني fan-out متوازيًا.
6. افحص سجلات التشغيل والأدلة، ولا تعتبر استجابة الموديل شهادة جودة.

| الواجهة البرمجية | الغرض |
| --- | --- |
| `POST /api/agents` | حفظ تعريف وكيل مخصص. |
| `PUT /api/agents/{id}/skills` | استبدال تعيينات المهارات؛ أرسل المجموعة الكاملة المراد الاحتفاظ بها. |
| `GET /api/agents/{id}/effective-configuration` | مراجعة الدور والتعليمات والمهارات والمنح المجمعة. |
| `PUT /api/workflows/{id}` | حفظ `WorkflowDetail` بما فيه `Workflow` و`Stages` و`Edges`. |
| `GET /api/workflows/{id}` | قراءة التعريف الكامل. |
| `POST /api/workflows/{id}/run` | تشغيل التعريف بطلب `Input`. |
| `POST /api/council/default/run` | تشغيل القالب الثلاثي، وليس الفريق المخصص. |

واجهات الإدارة تتطلب رمز الإدارة المحلي. وجود API لا يعني وجود مصمم Workflow مرئي كامل. المرحلة التي تحمل `RequiresApproval` تُرفض قبل تشغيلها؛ لا يوجد حاليًا مسار استئناف يستهلك موافقة مرتبطة بها.

## 6. حوكمة الأدوات: التنفيذ وحدوده

لا يوجد dispatcher عام يحول tool calls من الموديل إلى أوامر Shell. تسجيل معرف ضمن المنح لا ينشئ أداة تنفيذية. لذلك لا يصح الادعاء بوجود محرك ينفذ أي أمر مسجل ثم يطلب الموافقة تلقائيًا على الباقي.

| الحالة | السلوك الموجود |
| --- | --- |
| مهارة تعليمية افتراضية | لا تمنح أدوات. |
| مهارة ToolBacked تفتقد منحة مطلوبة | تُرفض أثناء تجميع إعدادات الوكيل. |
| قراءة ملف Workspace | مسار حقيقي يتطلب المنحة والجذر المسموح وقيود الملفات. |
| `ToolPolicy`: قراءة ممنوحة | يسمح قرار السياسة. |
| `ToolPolicy`: كتابة أو خروج شبكي ممنوح | القرار يشترط موافقة؛ ليس تنفيذًا تلقائيًا أو نافذة موافقات مكتملة. |
| عملية بلا sandbox | مرفوضة حتى عند وجود منحة. |
| أداة تدميرية | مرفوضة افتراضيًا حتى عند منحها. |
| MCP | سياسة ثقة ومنحة وفحص أولي لوصف schema؛ ليست عميلًا حيًا أو تحقق JSON Schema كاملًا. |

غياب المنحة يعني الرفض، وليس التحويل التلقائي إلى طلب موافقة. وجود المنحة لا يلغي موافقة الآثار الجانبية. `ApprovalGate` يتحقق من حالة الموافقة وانتهائها في المسارات التي تستخدمه، لكنه ليس محرك تفويض شاملًا لكل الأدوات.

المسار المستهدف لأي dispatcher مستقبلي: التحقق من تسجيل الأداة، ثم المنحة والنطاق والمدخلات، ثم المخاطر والموافقة المرتبطة بالإجراء، ثم التنفيذ المقيد والتدقيق. الأداة المجهولة تُرفض، والموافقة وحدها لا تعوّض غياب المنحة.

`git push` وDB migrations ليست أوامر ينفذها النموذج في المحرك الحالي. غياب منفذ عام لها مختلف عن وجود sandbox وحاجز موافقات شامل اختُبر ضد انحراف السياق.

## 7. السجلات والأمان

SQLite يحفظ تشغيلات الوكلاء ورسائل الجلسات والموافقات وتدقيق طلبات الإدارة المعدّلة. تدقيق الإدارة يستبعد أجسام الطلبات والمفاتيح، لكنه ليس سجل تنفيذ شاملًا مقاومًا للعبث لكل أداة. الرسائل والمخرجات مخزنة منفصلًا؛ تجنب إرسال الأسرار داخل البرومبت.

رمز الإدارة المحلي ليس هوية متعددة المستخدمين أو RBAC لكل شخص. احتفظ بالخدمة على loopback ولا تعرضها للإنترنت. راجع [استعادة الدخول](AUTH_RECOVERY.md) و[اتصالات الموديلات](PROVIDER_CONNECTIONS.md).

## 8. قائمة قبول للمشغّل

- [ ] الاتصال والموديل والتكلفة المتوقعة معروفون لكل وكيل.
- [ ] الدور والنمط والمهارات والمنح الفعلية تمت مراجعتها.
- [ ] الفريق المخصص مرتبط بـWorkflow مخصص، لا زر القالب الثلاثي فقط.
- [ ] الاعتماديات وقوائم التحقق والأدلة المتوقعة محددة.
- [ ] المراجعة مستقلة والادعاءات غير المثبتة مسجلة كقيود.
- [ ] الحماية من الآثار الجانبية لا تعتمد على تعليمات الموديل وحدها.
- [ ] التقرير يذكر المنفذ وغير المختبر وما يحتاج موافقة بشرية.

## 9. مرجع التحقق وحدود هذه المراجعة

مصادر التنفيذ: `src/DragonKMG.Application/DefaultCouncil.cs` و`PlatformService.cs` و`WorkflowValidator.cs`، ومسارات `src/DragonKMG.Api/Program.cs`، وسياسات `src/DragonKMG.ToolGateway/ToolPolicy.cs` و`ApprovalGate.cs` و`McpTrustPolicy.cs`.

اختبارات مرجعية: `tests/DragonKMG.Tests/DefaultCouncilTests.cs` و`SafetyTests.cs`. هذه مراجعة توثيقية للمصدر؛ لا تدعي إعادة تشغيل اختبارات التكامل أو المزودين الحيين. التوازي، التوجيه الشرطي التلقائي، قفل الملفات، الاعتماد البرمجي بخمسة أدوار، وعميل الأدوات العام قدرات غير مكتملة وليست وعودًا للإصدار الحالي.
