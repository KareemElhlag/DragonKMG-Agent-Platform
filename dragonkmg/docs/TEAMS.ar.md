# الفرق المسماة وتوجيه مهام الجلسة

## الفكرة

الفريق تعريف دائم باسم ووصف وقائمة وكلاء مرتبة. يمكن إنشاء فرق للتخطيط والمراجعات والتنفيذ أو أي استخدام آخر، مع إعادة استخدام الوكيل نفسه في أكثر من فريق. الفريق لا يضيف صلاحيات جديدة لأعضائه؛ كل عضو يحتفظ بدوره وموديله واتصاله ومهاراته ومنحه.

لا تُنشأ فرق افتراضية أو تُختار تلقائيًا نيابة عن المستخدم. قالب المجلس الثلاثي القديم يظل مسارًا منفصلًا؛ الفرق المسماة ليست محصورة في أعضائه.

## الإعداد في الداشبورد

1. افتح تبويب الفرق وأنشئ فريقًا باسم مميز.
2. اختر أعضاءه وحدد ترتيب التنفيذ ثم احفظ.
3. افتح الجلسة واختر فريق الطلب، أو احفظ فريقًا افتراضيًا لهذه الجلسة.
4. أرسل المهمة؛ أعضاء الفريق المحدد فقط يعملون بالتتابع. بقية الفرق لا تعمل.

اختيار فريق لطلب لا يغير افتراضي الجلسة. تعديل الافتراضي عملية صريحة، ويمكن إزالته. إذا غاب تحديد الفريق وافتراضي الجلسة، يطلب النظام الاختيار ولا يستدعي أي موديل. الفريق المعطل أو غير الصالح لا يؤدي إلى اختيار فريق بديل من نفسه.

## تحديد الفريق داخل البرومبت

اكتب الأمر في أول سطر، والمهمة في السطر التالي:

```text
/team فريق التخطيط
ضع خطة مراجعة لإدارة المخزون دون تنفيذ تغييرات.
```

يمكن استخدام معرف الفريق بدل اسمه. هذا توجيه صريح، وليس اكتشافًا لغويًا حرًا لعبارات مثل «خلي فريق كذا يعملها». التحديدان المتعارضان من الحقل والأمر النصي يُرفضان بدل اختيار أحدهما بصمت. إذا كان الاسم ملتبسًا بين أكثر من فريق، استخدم المعرف الكامل.

## الترمينال

- `/teams`: أسماء الفرق ومعرفاتها وعدد الأعضاء وحالتها.
- `/team use <name-or-id>`: حفظ افتراضي الجلسة؛ الاسم قد يحتوي مسافات.
- `/team clear`: إزالة الافتراضي، فتعود ضرورة الاختيار قبل إرسال المهمة.
- `/team send <full-team-id> <prompt>`: توجيه طلب واحد دون تغيير الافتراضي.

الأوامر `/use` و`/model` و`/mode` تبقى لإدارة إعدادات الوكيل؛ اختيار وكيل وحده لا يعوّض اختيار فريق لمحادثة الفرق. `/quick` مقصور على فريق من عضو واحد، وليس اختصارًا يسقط مراجعات فريق متعدد الأعضاء.

## الحدود والحماية

- التنفيذ متتابع، وليس متوازيًا. يتلقى كل عضو الطلب وأدلة محدودة من السابقين.
- فريق من عضو واحد مناسب للمحادثة الاقتصادية؛ زيادة الأعضاء تزيد استدعاءات الموديل ولا تعني توفير التوكنز.
- لا يبدأ فريق آخر إلا بطلب آخر أو تغيير صريح للتوجيه.
- الجلسة تسمح بطلب جارٍ واحد؛ لا يُعاد إرسال المهمة تلقائيًا بعد الخطأ.
- انتهاء استدعاء عضو بنجاح لا يثبت أنه كتب ملفات أو نفذ اختبارات؛ ذلك يحتاج أدوات وأدلة فعلية.
- الحفظ يستخدم إصدار التعريف لمنع استبدال تعديل أحدث بصمت. أعد التحميل عند تعارض التعديلات.
- المهارات والصلاحيات وحدود الشبكة لكل وكيل تظل سارية.
- حالة تفعيل جميع الأعضاء تُفحص قبل البدء؛ الإعدادات والاتصال والمهارات تُفحص عند استدعاء كل عضو. التشغيل ليس معاملة ذرّية: فشل عضو لاحق لا يلغي تكلفة أو مخرجات عضو سبقه.
- `runId` و`instructionCharacters` و`source` في رد API تخص آخر عضو، وليست إجمالي استخدام الفريق. `elapsedMs` يقيس الطلب كله. إثبات الفريق ونسخته وترتيب أعضائه محفوظ في سجل المحادثة.

## الواجهات البرمجية

| المسار | الغرض |
| --- | --- |
| `GET /api/teams` | قراءة الفرق. |
| `PUT /api/teams/{id}` | إنشاء/تعديل فريق: `id`, `name`, `description`, `enabled`, `agentIds`, `version`. |
| `GET /api/sessions/{id}/team` | قراءة `teamId` الافتراضي أو `null`. |
| `PUT /api/sessions/{id}/team` | حفظ `{ "teamId": "..." }` أو مسحه بـ`null`. |
| `POST /api/sessions/{id}/messages` | إرسال `input` و`teamId` اختياري؛ غياب الاثنين: التحديد الصريح والافتراضي، ينتج `TeamRequired`. |

هذه واجهات إدارة محلية محمية برمز الإدارة، وليست نظام تعدد مستخدمين. لا تضع مفاتيح الموديلات في تعريف الفريق أو البرومبت. راجع [حوكمة التشغيل](MULTI_AGENT_GOVERNANCE.ar.md).
